# Tally recurring obligations implementation plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Make fixed/variable recurring periods, manual period payments and automatic/confirmed/failed deductions work without an open client, preserving every period and financial event.

**Architecture:** Reuse owner-scoped canonical commands, permanent receipts and immutable payment/reversal records. An anchored civil-calendar engine supplies deterministic occurrences; persisted fenced jobs materialize bounded batches and process one scheduled automatic event per instance. Typed repositories/providers expose these operations through the original responsive UI.

**Tech Stack:** Existing Flutter/Riverpod/go_router/FlutterFire; TypeScript Firebase Functions v2/Admin, Node22; locked timezone0.11.1 and shared IANA2026c transition tables; demo-tally emulators. Task1's evidenced timezone ruling replaced the originally proposed Temporal/ICU adapter; see docs/architecture/recurrence-contract.md.

**Spec:** docs/superpowers/specs/2026-10-03-tally-design.md; docs/architecture/financial-engine.md; docs/architecture/firebase.md; docs/quality/testing-and-operations.md; docs/product/experience.md; .lavish/tally-design.{html,css,js}. This executes the already-authorized M4 roadmap. M5–M8 remain required before launch.

## Global Constraints

- Work on main only; preserve unrelated .ignore. Continuous implementation and eventual deployment are already authorized; no new branches/worktrees or repeated milestone approvals.
- Seven currencies, integer individual money1..1_000_000_000_000; aggregates<=9_007_199_254_740_991. Unknown bill amounts remain null, paid0, remaining null, closed false. Recurring templates have null lifetime principal/paid/remaining.
- Civil dates YYYY-MM-DD1900–2199; saved instance zone survives profile changes. Recurrence uses original anchor, calendar-month clamping recovers, end dates inclusive.
- Frequency weekly/biweekly/monthly/quarterly/yearly/custom. Canonical standard unit/interval: weeks1/weeks2/months1/months3/years1. Custom days/weeks/months/years, interval1–365. At most one occurrence per civil date.
- Rule fields frequency, interval, unit, anchorDate, preferredDay, monthEnd, timezone, localDeductionTime, startDate, endDate, ruleVersion. State additionally generationCursor (last considered occurrence index; initial-1), generatedThrough (last materialized original date|null), pauseRanges (start inclusive/end exclusive|null, <=120) and active/paused/ended lifecycle. Date-only billing labels are not identities.
- Occurrence key r:YYYY-MM-DD and existing occurrenceInstanceId hashing. Never reuse an existing occurrence with changed terms; changing a due date does not change identity.
- First eligible occurrence materialized on creation if within today+90 days; catch-up retains missed historical periods. Maximum30 newly generated documents per transaction, checked active owner/template/job lease and rule revision; persistent continuation and bounded worker wall time.
- Template amount/source/category/reminder changes affect only newly generated periods. Existing periods, including future periods, keep snapshots. Explicit unpaid-period edits carry revisions and immutable activity. Schedule changes retain the original anchor and apply after the last materialized occurrence; no earlier cutover without separate explicit cancellation.
- Pause/end retain existing periods/history; UI previews retained future rows. Resume excludes paused ranges. Failure never causes the original scheduled event to run again.
- Manual payments choose exactly one recurring instance. Full reversals/corrections preserve the original instance, amounts, snapshots and provenance. Never silently move a repayment to another month.
- Automatic means an assumption, not a bank event. Form copy: **Tally will record this as paid on its schedule. You can correct it if the deduction fails.** Automatic with confirmation is the initial automatic choice. No bank integration.
- Known automatic remainder creates one assumed payment; confirmation creates expected attempt only; missing amount creates expected/needed only. Late variable amount requires confirmation. Failed assumed event appends one full reversal. Manual partial before auto leaves only the remainder; paid/skipped/cancelled periods suppress scheduled money.
- Resolve DST gap at first valid local instant after gap; overlap at earlier instant. Shared TypeScript/Dart fixtures pin this explicitly. Keep runtime/library timezone versions documented and release canaries checked.
- All scheduled writes recheck ownership/active profile and current state inside transactions. Receipts, ledger revision, caches, attempts/activity and jobs commit together. Append-only history is never overwritten.
- Prompt job worker uses same persisted lease as scheduled recovery; all dispatchers obey a total450-second work budget within540-second function timeout. Stop claiming new work without enough180-second projection budget. Never process25 sequential180-second scans blindly.
- Notification jobs are generated now; actual FCM/inbox delivery belongs to M5. Financial forms remain online-only until M6. Pending live billing/region inputs do not block emulator implementation.
- Maintain original Lavish palette, bundled fonts, shell and Home composition. Small forms/panels, human labels, light/dark/mobile/tablet/desktop; no direct Firebase calls in widgets.

## Review Focus

1. Template edits/pause/end/profile locks race generation: current transaction state wins and stale workers cannot generate forbidden or altered-history periods. Task2 emulator contention tests.
2. Automatic payment races manual payment, confirmation or failure: exact outstanding remainder, one receipt/event, no duplicate payment or negative balance. Task3 contention/replay tests.
3. A variable amount arrives after the scheduled time or an assumed payment was reversed: no retroactive assumption and no consumed automatic event runs again. Tasks3/4 tests.
4. Multi-year daily backlog, duplicate workers and expired leases: bounded catch-up continues without skipped history; late worker cannot commit or finish newer work. Task2/3 tests.
5. DST gap/overlap/skipped civil day, leap/month-end and profile-zone change: Dart/server agree and saved dates/occurrence IDs never shift. Task1 fixtures and Task4 widget tests.
